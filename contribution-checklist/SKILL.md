# Contribution Checklist

Make the request understandable to someone who knows neither the project nor the conversation.

## State the ask first

Start an action request with who should do what and the expected result. Put background afterward.
When explaining outreach to the user, identify their goal, the destination's purpose, and the recipient action you propose.
Distinguish these requests:

- An editor: consider publishing a project update or contributor link.
- A developer: implement a specific change in the project's repository.
- A tester: reproduce a stated behavior and report the result.

Marketing is an objective, not an implementation task. Do not silently replace a marketing request with feature recruitment.
Choose a contribution task only when it serves the project's actual direction. Never invent work merely to qualify for coverage.

## Before a contribution call

Read the destination's current submission guidance. Identify which section fits the intended request.
A newsletter repository can accept an editorial link without requesting code for the newsletter itself.

- [ ] **What is the ask?** State one bounded change, its observable result, and what is outside scope. Lead with this sentence.
- [ ] **Where does someone start?** Link the actual source files or functions. Give the shortest setup and reproduction steps, then a practical first increment. Check that the links and steps are current.
- [ ] **Is mentoring available?** Confirm who can answer implementation questions and review changes. State the actual offer or absence of mentoring. Never promise someone else's time.

These are the three questions raised in [Nell Shamrell-Harrington's review](https://github.com/rust-lang/this-week-in-rust/pull/8915#issuecomment-6431438305).

## Check contributor readiness

Acceptance criteria support the ask; they do not replace an implementation starting point.
Keep the initial task proportional to the stated difficulty. Split large architectural work into a useful first contribution when possible.
Use concrete examples and necessary checks. Remove internal tracking jargon and long procedure lists from the opening.

Before submission, read it as a newcomer: can you explain the requested change, the first action, and the available help?
If a material answer is missing, prepare the draft locally and resolve the gap before submitting.
Use existing authorization only within its scope. Creating this checklist does not authorize sending, posting, or reopening anything.

When responding to feedback, answer the reviewer's concrete questions. Acknowledge what was unclear and point to actual revisions.
Do not answer a request for a bounded task with a general desire for traction, stars, or feature parity.
